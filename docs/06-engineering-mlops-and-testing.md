# 06 — Engineering, MLOps, and Testing

This page describes the implemented repository. The original phase plan and unbuilt methods remain
in the [roadmap](04-roadmap.md) and [method ladder](03-method-ladder-and-matrix.md).

## 1. Repository map

| Path | Responsibility |
|---|---|
| `configs/` | Base, dataset, model, and frozen recipe YAML |
| `src/inspector/data/` | Dataset discovery, official splits, transforms, and integrity audits |
| `src/inspector/models/` | Trivial baselines, convolutional autoencoder, PatchCore, and reference comparator |
| `src/inspector/metrics/`, `postproc/`, `robustness/` | Metrics, operating points, object region, and corruptions |
| `src/inspector/runner.py`, `pipeline.py`, `evaluate.py` | Resolved runs, fit/predict/evaluate, and stored predictions |
| `src/inspector/api/`, `app/` | Artifact export, FastAPI service, and Gradio demo |
| `scripts/` | Analysis and report drivers; `build_notebooks.py` generates both notebooks |
| `tests/` | CPU fixture tests, leakage checks, model checks, and reference agreement |
| `reports/runs/` | Per-run specifications, results, and predictions |
| `reports/studies/`, `reports/eda*`, `reports/case-book/` | Derived analyses and interpretation |
| `data/manifests/` | Tracked split manifests; `data/raw/` contains ignored dataset bytes |

The CLI in `src/inspector/cli.py` exposes `fetch`, `fixtures`, `audit`, `eda`, `run`, `results`,
`study`, `export`, `serve`, and `demo`. The notebooks are thin drivers
of the same package and are regenerated by `python scripts/build_notebooks.py`.
The empty `src/inspector/features/` package is retained because its bytes are part of existing
run IDs; removing it would make completed runs appear to be a different implementation.

## 2. Run identity and results

Configs compose from `configs/base.yaml`, a dataset file, a model or recipe file, and explicit
overrides. `inspector run` resolves the effective model, transform, evaluation settings, seed, and
split listing before fitting. The resolved `RunSpec` plus the source hash of result-producing code
determines the run ID. A completed run resumes by that ID; failed runs retain their reason.

`reports/runs/<run_id>/` contains `spec.json`, `result.json`, and per-split prediction JSON. Raw
float16 maps are `.npz` files in the same folder and are ignored by Git because of their size.
Run records include the resolved specification, code and environment provenance, threshold source,
and timing/memory fields. See [the experiment plan](11-experiment-plan.md) for the protocol rules.

`inspector results` regenerates `reports/results_registry.csv` from the run registry. That CSV is
the current table; its exact columns are defined in `src/inspector/results.py`. The older synthetic
and pre-v2 VisA tables are retained under `reports/archive/` with their limitations documented
there. MLflow is an optional local tracker in `src/inspector/tracking.py`; it is not the source of
truth for the current table.

## 3. Memory budget

On the RTX 3050, a WideResNet50-2 `layer2+layer3` forward pass at native VisA resolution
(1404×1070) was measured below 1 GB VRAM at batch size 1. Host RAM is the tighter limit:
23,584 patches per image across 768 training images would occupy about 37 GB even in fp16.
PatchCore therefore samples candidates while extracting and records peak host RSS per stage.
The measured input costs and the correction to the original VRAM assumption are in
[P3 findings](../reports/P3-visa-findings.md).

The current recipe uses a fixed 10,000-patch bank. Treat any new input resolution, feature layer,
or bank size as a new resolved run so old results are not silently reused.

## 4. Tests and CI

`pytest` uses generated synthetic fixtures; the default suite needs neither dataset bytes nor a
GPU. It covers split leakage, metric invariants, threshold ranks, source identity, model scoring,
reference agreement, evaluation, and notebook regeneration. Real-data or slow tests use pytest
markers in `pyproject.toml`. The [CI workflow](../.github/workflows/ci.yml) runs:

- a history-aware dataset license guard;
- Ruff and mypy;
- the core suite on Linux and Windows with Python 3.10–3.12;
- deep-model CPU tests without pretrained weight downloads;
- a CLI fixture generation and audit smoke test.

The earlier roadmap mentions golden files and a Docker smoke job. They are planned gates, not
present CI jobs.

## 5. Serving

`inspector export` fits one category and saves the model bank plus `meta.json`, including the
threshold calibrated on validation normals. `inspector serve --artifact ...` loads that artifact
and exposes `GET /health` and `POST /predict`; `inspector demo` uses the same artifact in Gradio.
Input exposure and focus guards can return `decision: refused`. See [README](../README.md#serving)
for commands and response behavior.

The [Dockerfile](../Dockerfile) builds a CPU inference image, downloads backbone weights at build
time, and mounts the fitted artifact read-only at runtime. Dataset images and fitted banks are not
baked into the image.
